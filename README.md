# Bond Watch · 中美日国债监控

监控中国、美国、日本三国主权债收益率曲线、期限结构、跨国利差与异动告警。跑在 GitHub Actions 上，每交易日更新，产出静态看板、JSON/CSV 数据、README 摘要与可选邮件日报。

数据源全部免费公开，**不需要任何 API key**。

## 数据源

| 市场 | 来源 | 期限 | 说明 |
| --- | --- | --- | --- |
| 中国 | [东方财富数据中心](https://data.eastmoney.com/cjsj/zmgzsyl.html) | 2Y / 5Y / 10Y / 30Y | 日频 |
| 美国 | [FRED](https://fred.stlouisfed.org/) `DGS2/5/10/30`（东财为镜像） | 2Y / 5Y / 10Y / 30Y | 单一权威源 |
| 日本 | [日本财务省 MOF](https://www.mof.go.jp/english/policy/jgbs/reference/interest_rate/) | 1Y–40Y（取 2/5/10/30Y） | 官方 CSV |

关于数据源的几个实现要点：

- **东财的期限字段没有语义**。返回值里期限是 `EMM00166466` 这类不透明 id，且顺序与期限不对应。好在同一接口也发布 10Y-2Y 利差列，用它做恒等式校验能唯一确定映射（已在 468/468 行上验证）。`validate_eastmoney_mapping()` 每次运行都会重跑这个校验，若上游字段重排会直接报错并回退到缓存，而不是发布错标的曲线。
- **MOF 把序列拆成两个文件**。`jgbcme.csv` 只含当月但最新，`historical/jgbcme_all.csv` 有 1974 年至今的全历史但滞后数周。脚本两个都抓，当月文件后写入以覆盖重叠部分。
- FRED 会在收到浏览器 User-Agent 时挂住直到超时，用普通 urllib 请求则立即返回，因此该源单独走 `browser_ua=False`。
- **美债不是双源冗余**。东财的美债列与 FRED 在 115 个共同交易日上差异全部恰好 0.0bp —— 真正独立的两个源不会如此，取数时点和舍入处理总会偶尔差 1bp。这说明东财是转发 FRED（或同一上游）。`compare_us_sources()` 仍然每天跑，但它只能确认"镜像没有搬错数"，不构成独立印证，永远返回 ok。美债数值本身是可靠的（FRED 发布美联储 H.15 官方数据），可靠性来自源本身权威，不是来自交叉验证。真要独立冗余得接[财政部官网](https://home.treasury.gov/interest-rates-data-csv-archive)的一手数据。
- **中国才是真正的单点故障**。三国里只有中国是单源、非公开 API、字段无语义（10Y/30Y 曾被我弄反过一次）。我试过 ChinaBond 做第二源但没成：那个接口无论传什么日期都返回同一份固定快照，且与东财有约 23.6bp 无法解释的差异（疑似政金债曲线或陈旧快照，无法确定，因此不能用）。

## 产出

```
data/yields.json    看板数据：各国曲线、期限结构、跨国利差、温度、告警、走势序列
data/history.csv    长表历史 (market,date,tenor,yield)，保留十年，走势图的数据源头
data/alerts.json    仅告警，便于外部工具消费
```

`yields.json` 目前 230KB，其中约 91% 是走势序列（三国 10Y + 四组利差，各两年 520 点）—— 这些完全可以从 `history.csv` 推导，等于同一份数据存了两遍，且每个交易日 commit 一次。短期无妨（`.git` 现在不到 1MB），但按每年 250 次提交、每次近全文改写累积，长期会把仓库推到几百 MB。干净的做法是前端直接读 `history.csv` 自己算，`yields.json` 回到 8KB 的纯快照。尚未实施。

## 抓取策略

日常运行只取增量：东财第一页 60 行（约三个月）、MOF 当月文件（1.2KB）、FRED 加 `cosd` 参数只回溯 45 天。历史已在 `history.csv` 里，没必要每天重下。实测增量约 2.6 秒，全量回补约 3 分钟。

抓的是重叠窗口而不是只抓当日，因为 `merge_series` 对已存在的日期走覆盖写入 —— 上游若修订了某天的值，本地会跟着改。只取当日的话，一旦某天发布后被修订，本地就永久停在错的数上。

东财的分页大小按模式分开：全量用 500 行/页（9322 行历史走 19 次请求，若用 60 行要 156 次），增量用 60 行/页。之前两者共用 500，导致每天重下近两年数据 —— 一页 500 行恰好横跨 690 天。60 行仍远高于映射守卫需要的 20 行下限，实测每次仍在 60/60 行上完成校验。

`needs_backfill()` 在这三种情况下自动切回全量：无缓存历史（冷启动）、某市场观测数不足 400（分位不可靠）、缓存落后超过 20 天（增量窗口可能补不上缺口）。

**数值合理性检查**：写入前筛掉超出 [-2%, 25%] 区间、恰好为 0（哨兵值）、或跳变超出容差的值。错数据比缺数据更糟 —— 它会静默污染分位和变动计算，而且会一直留在提交的历史里。被拒的值记在 `data_quality.rejected_values` 里。

跳变容差按间隔天数放宽（`100bp × √天数`，上限 400bp）：+110bp 隔夜是坏数据，隔一个月则完全正常。最初用固定 100bp，回补时误杀了 1716 个合法值 —— 东财早期历史的观测间隔长达数月，逐笔比较必然超限。零值检查放在跳变检查之前，否则周末放宽后的容差会把 0 放进来。

## 指标口径

**期限结构**：10Y-2Y、30Y-10Y、10Y-5Y，单位 bp。曲线形态按 10Y-2Y 分档：`< -25` 深度倒挂、`< 0` 倒挂、`< 25` 平坦、`< 100` 正常、其余陡峭。

**走势与曲线对比**：看板里每张国债卡都叠加了一月前和一年前的曲线（虚线），三条共用同一 y 轴刻度，所以能直接看出曲线是平移、陡峭化还是扭转 —— 平移、陡峭化和扭转都可能让 10Y 看起来没动。另有两年期的 10Y 走势和利差走势图，数据取自 `history.csv`。

**跨国利差**：中美 10Y、日美 10Y、中日 10Y、中美 2Y。只在两国都有报价的交易日计算，避免假期错配造成的跳空。

**债市温度（0-100）**：`50% 收益率分位 + 20% 曲线斜率 + 30% 一个月动量`。读数越高表示收益率相对自身历史越高且在上行，即金融条件收紧、债券承压；越低则相反。分位取过去约两年（504 个交易日）的滚动窗口。

> 权重是实验性的，未经回测验证，当作可读的相对指标而非交易信号。

温度计有一个已知缺陷：斜率项把陡峭化一律算作高分，但陡峭化有两种相反成因 —— 长端上行主导是熊陡（通胀预期/期限溢价上升，债券承压），短端下行主导是牛陡（降息预期，债券受益）。两者含义相反却得同一个分数。要区分需要看短端和长端各自的方向，尚未实现。

另有两项数据已在手但未使用：MOF 的 CSV 抓的是 1Y–40Y 全曲线，实际只用了 4 个期限，日本 40Y 超长端（当前全球债市焦点）被丢掉了；名义收益率也没拆成实际利率 + 通胀预期，FRED 的 `T10YIE`/`DFII10` 免费可取，拆开后解释力会强不少。

**异动告警**：按各市场自身波动率标准化，不用统一的 bp 阈值。

三国日波动差近一个数量级 —— 实测中国 10Y 日σ 约 0.7bp，美国 4.2bp，日本 3.8bp。统一用 ±10bp/日 的话，对中国是 13.7σ 事件（几年不触发一次，等于告警是死的），对美国只有 2.4σ（日常波动就报）。所以改成除以该期限自身过去 60 个交易日日变动的标准差：

| 类型 | 触发条件 |
| --- | --- |
| 单期限单日变动 | ≥ 2σ 且 ≥ 2bp（≥ 3σ 记为 high） |
| 单期限一周变动 | ≥ 2.5σ√5 且 ≥ 5bp |
| 跨国利差单日变动 | ≥ 2σ 且 ≥ 2bp |
| 绝对兜底 | 单日 ≥ 15bp 或一周 ≥ 35bp，记为 high |
| 10Y-2Y 倒挂 | 出现即告警 |

绝对下限（2bp/5bp）防止近乎静止的市场对统计噪音报警 —— σ 只有 0.3bp 时 2σ 没有意义。绝对上限则保证大幅变动无论波动率背景如何都会触发。阈值都在 `ALERT_RULES` 里。

周变动的 σ 直接用过去 60 个「5 个观测日跨度」的实际变动算，不是把日 σ 乘 √5。√5 假设日间独立，趋势市里不成立 —— 实测比值在 0.79（美国 2Y）到 1.25（中国 2Y）之间，用 √5 会让美债的周告警比标称的 2.5σ 更容易触发。

**数据陈旧告警**：任一市场最新观测超过 4 天未推进即告警（≥8 天记为 high）。降级设计会在数据源挂掉时沿用缓存继续出图，好处是看板不会空，代价是**故障表现为静默的陈旧** —— 页面照常渲染、邮件照常发送，只有日期不动。这条告警把这种情况变成显式信号，看板顶部会显示「数据陈旧 N 天」，邮件顶部也会有警示条。

> 春节等长假会让中国数据出现 10-11 天的正常间隔，届时会误报一次。我选择保留 4 天阈值而不是放宽到 12 天，因为后者会让真实中断藏上近两周。

告警文案会标注实际 σ 倍数，且当两个观测日跨越假期时写"N 日间"而非"单日"，避免把春节后横跨一周的变动标成日变动。

## 本地运行

```bash
python -m unittest discover -s tests     # 66 个单元测试，不联网
python scripts/update_yields.py          # 抓数、算指标、写 data/
python scripts/update_readme.py          # 刷新 README 快照区块
python scripts/send_daily_email.py --dry-run   # 生成 email_preview.html 不发信
python3 -m http.server 8000              # 打开 http://localhost:8000 看看板
```

脚本只用 Python 标准库，没有 `requirements.txt` 需要装。

测试覆盖回溯算术、波动率标准化、告警判定、数值筛查、跨源比对和东财字段映射守卫，全部用手工构造的序列，不联网。工作流每次触发都会先跑测试。

## 部署

1. 推到 GitHub，Settings → Pages → Source 选 **GitHub Actions**。
2. Actions 里手动跑一次 `Refresh yields and deploy Pages` 验证。
3. 工作流每周一至周五 08:10 UTC（北京 16:10 / 东京 17:10）运行，此时中日已收盘、MOF 当日曲线已发布；美债为前一交易日收盘值。

刷新后的 `data/` 与 README 会由工作流提交回仓库，因此历史会随时间累积。这需要 `contents: write` 权限，已在工作流中声明。

### 邮件日报（可选）

设 Variables `EMAIL_ENABLED=true`，并配置 Secrets：`SMTP_HOST`、`SMTP_PORT`、`SMTP_USERNAME`、`SMTP_PASSWORD`、`EMAIL_FROM`、`EMAIL_TO`（多个收件人用逗号分隔）。另可设 `SITE_URL` 指向你的 Pages 地址、`EMAIL_ONLY_ON_ALERT=true` 只在有异动时发信。

## 容错

每个数据源独立 try/except 并带三次重试。任一源失败时脚本沿用已提交的 `data/history.csv` 继续出图，并在 `data_quality` 里标记 `degraded` 与失败原因，看板顶部与邮件也会显示降级提示。只有在三源全挂且无任何缓存历史时才以非零码退出。

这个设计的代价是**故障表现为静默的陈旧而非响亮的失败** —— 页面照常渲染、邮件照常发送，只有数据日期不动。上面的数据陈旧告警就是为此存在的：4 天不推进即显式告警，看板顶部改显示「数据陈旧 N 天」。
